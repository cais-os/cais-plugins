# Scaffolding Preferences

These conventions apply to **every** Cais product — internal tools and
customer-facing apps alike.

## Prerequisites

Before applying this skill, also invoke:

- **`tech-stack-preferences`** — for the default framework and tooling choices
- **`team-conventions`** — for naming, commit messages, and documentation
  standards

## Monorepo Folder Structure

Every project uses a monorepo layout with an `apps/` directory. Framework files
live **inside** the app subdirectory, never at the repo root.

```
product-name/
├── .claude/
│   └── CLAUDE.md
├── apps/
│   └── web/                    # named by platform (see table below)
│       ├── public/
│       ├── src/
│       ├── .gitignore          # auto-generated by the framework
│       ├── components.json
│       ├── next.config.ts
│       ├── package.json
│       ├── pnpm-lock.yaml
│       ├── postcss.config.mjs
│       └── tsconfig.json
├── supabase/                   # Supabase migrations (most projects)
├── .gitignore                  # root monorepo gitignore
└── README.md
```

When a project has multiple apps, each gets its own subdirectory:

```
product-name/
├── apps/
│   ├── web/                    # Next.js frontend
│   ├── mobile/                 # Expo app
│   └── api/                    # Express backend
├── supabase/                   # Supabase migrations
├── .claude/
│   └── CLAUDE.md
├── .gitignore
└── README.md
```

> **Note:** `supabase/` is shown here because most Cais products use Supabase.
> However, do not pre-create it — only add it when the project actually needs
> Supabase (via `supabase init`). Landing pages and purely static sites typically
> don't need it.

## App Naming Convention

Name apps by **platform**, not by function. A single Next.js app can serve both
a landing page and a dashboard — call it `web`, not `landing` or `dashboard`.

| Name     | Framework | When to use                |
| -------- | --------- | -------------------------- |
| `web`    | Next.js   | Any web application        |
| `mobile` | Expo      | Mobile app (iOS / Android) |
| `api`    | Express   | Standalone API server      |
| `docs`   | Varies    | Documentation site         |

If a project only has one app, still put it inside `apps/`. This keeps the
structure consistent and ready for growth.

## Root `.gitignore`

The root gitignore covers monorepo-wide concerns. Create this file at the repo
root with the following content:

```gitignore
# superpowers brainstorm
.superpowers/

# remember
.remember/

# docs
docs/
```

## App-level `.gitignore`

Each app inside `apps/` gets its own `.gitignore` automatically when scaffolded
by its framework (e.g., `create-next-app`, `create-expo-app`). Do not manually
create or override these — the framework generates the correct entries for its
platform. Just verify the file exists after scaffolding.

## Terminal Layout

Use `templates/terminals.json` from this skill as a **reference** to create
`.vscode/terminals.json` for the project. Do not copy it verbatim — assess which
services the project actually uses and build the terminals list accordingly:

- Include only terminals for services the project needs
- Adapt commands, paths, and URLs to match the project's actual configuration
- Follow the ordering and grouping conventions below

### Ordering convention

Terminals are ordered by startup priority:

1. **Web dev server** — `cd apps/web && pnpm run dev`
2. **Backend** — Trigger.dev, Express, or other backend service
3. **Database** — `supabase start`
4. **Edge functions** — `supabase functions serve` (split with database)
5. **Payments** — Stripe CLI (empty command, manual use)
6. **Webhooks** — Stripe listener (split with payments)
7. **Tunnels** — ngrok instances, named `ngrok-<service>`
8. **Regular terminal** — `zsh`, always last, with `focus: true`

### Split terminal grouping

Use the `split` property to group related services in the same terminal panel:

- `edge` splits with `supabase` — both are Supabase services
- `webhooks` splits with `stripe` — webhooks listen for Stripe events

### Conventions

- `autorun: false` — don't start terminals automatically
- `autokill: true` — kill terminals when VS Code closes
- Terminal names are lowercase, single-word or `ngrok-<target>`
- **Always end with a `zsh` terminal** — every `terminals.json` MUST close with a
  plain shell entry. This is non-negotiable, even for minimal projects that only
  have one or two service terminals:

  ```json
  {
    "name": "zsh",
    "description": "The regular terminal",
    "focus": true,
    "command": ""
  }
  ```

  It must use an empty `command` and `focus: true` so the developer lands in a
  ready workspace shell when the terminals boot. No other terminal should have
  `focus: true`.

## Scaffold Checklist

Follow these steps in order when scaffolding a new project:

1. **Initialize git** — `git init` in the project root
2. **Create root `.gitignore`** — from the template above
3. **Scaffold the framework** inside `apps/<platform>/`:
   - Next.js: `pnpm create next-app@latest apps/web`
   - Expo: `pnpm create expo-app apps/mobile`
   - Express: manually create `apps/api/` with `pnpm init`
4. **Verify app-level `.gitignore`** — ensure the framework scaffold created
   one; if not, add it manually
5. **Create `.claude/CLAUDE.md`** at the repo root documenting:
   - The stack chosen for this project (with any deviations from the default and
     why)
   - Key architectural decisions made during scaffolding
   - Any project-specific conventions to follow going forward
   - **Keep this file alive** — update CLAUDE.md continuously as the project
     evolves. Every significant architectural decision, new convention, or
     deviation from the default stack should be reflected here so future
     conversations always have accurate context
6. **Set up `.vscode/terminals.json`** — copy from `templates/terminals.json`
   and adapt to the project's stack
7. **Create `README.md`** — focused on setup and usage instructions
8. **Install dependencies** — `cd apps/<platform> && pnpm install`

## What NOT to Pre-create

Do not create these directories upfront. Add them only when they're actually
needed:

- **`packages/`** — only when two or more apps share code
- **`supabase/`** — only when the project adds Supabase (`supabase init`). When
  created, it goes at the **repo root** (next to `apps/`), not inside an app
- **`.github/`** — only when CI/CD workflows are configured
- **`.vscode/`** — only if adding `terminals.json` or shared settings
